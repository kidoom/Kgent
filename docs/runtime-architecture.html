Kgent Runtime 架构导读

用分层图、状态机和时序表，把 agent 运行时讲清楚——不用啃长文。

run_manager.py host.py loop.py ws_server.py

一句话

前端通过 WebSocket 发命令 → ws_server 解析 → RunManager 管状态和权限等待 → loop 跑 agent 逻辑 → 事件推回前端。

核心矛盾 & 解法

矛盾：loop 写起来像同步代码（await 等权限），但 WebSocket 是异步、跨网络的。

解法：RunManager 用 asyncio.Future 做桥——loop 阻塞在 Future 上，客户端稍后回复，Future 被唤醒，loop 继续跑。

谁负责什么（速查）

文件层级一句话
ws_server.py传输层WebSocket 协议、JSON 命令、推事件给客户端
run_manager.py调度层run 状态机、事件历史、权限 Future 阻塞/唤醒
loop.py业务层模型调用、工具执行、多轮循环
host.py适配层把 loop 和外部 IO 隔开（CLI / 测试用实现）

四层架构（从上到下）

数据和控制流大致如下，越往上越靠近用户，越往下越靠近 agent 核心。

传输层 transport/ws_server.py 收 JSON 命令，推 JSON 事件
↓ 调用 / 订阅
调度层 runtime/run_manager.py 管 run 生命周期 + 权限等待
↓ RunManagerHost 适配
业务层 runtime/loop.py run_agent_stream() 核心循环
↓ AgentHost 接口
适配层 runtime/host.py + RunManagerHost emit / request_permission / check_cancelled
注意：RunManagerHost 定义在 run_manager.py 里，不在 host.py。WebSocket 路径用的是前者；CLI 和测试用的是 host.py 里的实现。

各文件详细职责

ws_server.py
对外接口 · 知道 WebSocket
  • 监听 ws://127.0.0.1:8765/runtime
  • 解析 start_run / permission_decision / cancel_run
  • subscribe 事件 → 推给客户端
  • 断线时 cancel_runs_for_connection
run_manager.py

  • 内存里维护所有 RunState
  • record_event 存历史 + 广播
  • wait_for_permission 阻塞 loop
  • resolve_permission 唤醒 loop
loop.py
Agent 大脑
  • 多轮 model → tool → observe
  • 通过 host.emit 发步骤事件
  • 权限 ask 时 await host.request_permission
  • 每轮 check_cancelled
host.py
IO 适配（非 WS 路径）
  • AgentHost 协议定义
  • CollectingHost → run_agent() 测试/同步
  • CLIHost → debug 命令行
  • build_permission_request 等 helper

RunManager 是什么

进程内的 run 监督器（supervisor）。每个 agent 运行 = 一个 run，有独立的状态、事件历史和最多一个 pending 权限请求。

RunState — 一个 run 的账本

run_id
唯一标识
session_id
对话会话
status
当前状态（见下方状态机）
events[]
完整事件历史，可回放
seq
最大事件序号
pending
正在等的权限 Future（最多 1 个）
connection_id
绑定的 WS 连接，断线清理用

状态机

running → waiting_permission → running → completed
running → cancelled 或 failed

只有 running 和 waiting_permission 可以被 cancel。

五个关键方法

create_run(session_id, connection_id)
登记新 run，返回 run_id。ws_server 收到 start_run 时调用。
record_event(event)
事件中枢：存历史 → 更新 status → 通知所有 subscriber（ws 推给前端）。run 结束时清理 subscriber。
wait_for_permission(request)
创建 Future，发 permission_required 事件，然后 await 阻塞。loop 卡在这里，等用户回复。
resolve_permission(run_id, id, decision)
客户端回复 allow/deny → future.set_result() → loop 被唤醒，继续执行或拒绝工具。
cancel_run(run_id)
标记 cancelled；如有 pending 权限则 deny 掉 Future，避免 loop 永远挂起。

RunManager 的三个索引

字典用途
_runsrun_id → RunState
_connection_runsconnection_id → 该连接下所有活跃 run
_subscribersrun_id → 回调列表（ws_server 注册，收到事件就推送）
局限：全是进程内存，重启即丢失。适合单机开发/debug，不是分布式调度器。

AgentHost 接口（三个方法）

loop 只认这个协议，不关心背后是 WebSocket 还是终端：

emit(event)
推送 agent_step、run_finished 等事件
request_permission(request)
工具需要用户确认时阻塞等待
check_cancelled()
每轮循环检查是否被取消

四种 Host 实现对比

实现定义位置用于权限怎么处理
RunManagerHost run_manager.py WebSocket 前端 Future 阻塞，等客户端 permission_decision
CLIHost host.py debug 命令行 终端 stdin 问 [y/N]
CollectingHost host.py run_agent() / 测试 自动 deny（不支持交互）

完整交互时序

用户发消息 → agent 要调高风险工具 → 用户点允许 → 拿到最终答案。

# 谁 做什么 结果
1 前端 发 start_run —
2 ws_server create_run + subscribe + 启动 run_agent_stream run_id 生成
3 loop emit(run_started) → 调模型 → emit(agent_step) 前端看到思考/步骤
4 loop 工具权限 = ask → host.request_permission() loop 阻塞 ⏸
5 RunManager 发 permission_required → subscriber 推 WS 前端弹权限对话框
6 前端 发 permission_decision {allow} —
7 RunManager resolve_permission → future.set_result(allow) loop 唤醒 ▶
8 loop 执行工具 → 继续循环 → emit(run_finished) 前端显示最终答案
